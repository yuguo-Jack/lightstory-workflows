# Game UI Design

基于上游 Game UI/UX 作 Codex 与本机制作链适配，[来源和改动](references/sources.md)。让玩家在需要时看到正确的信息、完成操作，并顺畅回到游戏。用户指定的世界观与美术方向优先，不能让通用 UI 模板决定游戏风格。

## 工作顺序

1. 读项目玩法、美术规范、目标平台/输入与已有界面。确定玩家当前需要作出的决策，再选择HUD、菜单、世界内界面或混合方式；不因“沉浸”强行隐藏重要信息。
2. 画适用的屏幕/状态流：进入、游玩、暂停、设置、载入、失败/完成等，以及背包、对话、任务等项目确实需要的界面。写清打开、返回、确认、取消和恢复路径，不自动添加商城、账号或社交系统。
3. 先做可交互线框或灰盒HUD，绑定真实游戏状态。将资源、冷却、任务和交互提示映射到明确的数据/事件；分开显示层与游戏规则。
4. 按[布局与交互检查](references/layout-and-flow.md)覆盖焦点、输入归属、弹窗、空/禁用/锁定/错误状态、缩放、安全区、长文本及本地化。只支持项目需要的设备，但每个宣称支持的设备都能完成必要流程。
5. 依据项目美术规范实现字体、图标、面板、选中/警告及反馈；重点信息在真实场景、运动、亮暗与特效背景下仍可读。视觉稿或AI生成的文字不能替代正式字体、真实数值和组件。
6. 用[本机执行映射](references/engine-integration.md)接入既定UE或Web工程；检查真实输入、状态变化和返回游戏，再在目标构建、显示尺寸及设备上验证。记录哪些实际测过，不能用截图或扫描规则代替操作验证。

## 交付与分工

简单修改沿用项目记录；多屏系统保留屏幕/状态图、组件与数据职责、交互/焦点规则、样式约定和验证结果。通用设计不强制每次生成独立规格文档。

- 玩法目标含糊或选择没有意义：配合 [Game Design Theory](../game-design-theory/SKILL.md)。
- 色彩、形体、图标与世界观不一致：配合 [Game Art Direction](../game-art-direction/SKILL.md)。
- 全项目沿用 [Game Production Workflows](../game-production-workflows/SKILL.md)。Web由Game Studio及其UI/试玩技能继续实现；UE使用已连接的Unreal技能。
- 复杂图标、道具图、立绘和背景可按需用本机ComfyUI生成，再规范化、切图、处理透明度；九宫格、字体、交互命中区和动态状态由确定性工具及运行端实现。已有可用素材直接复用。

已授权实现的任务继续到可操作并检查通过；纯设计任务给出可供开发使用的明确方案。审美是否符合个人预期与功能是否通过分别记录。
