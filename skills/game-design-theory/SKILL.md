# Game Design Theory

将用户想要的体验转成规则、可观察行为和迭代依据。基于上游 Game Design 模块作本机适配；[来源和改动](references/sources.md)。这提供分析工具，不以理论名词、文档数量或自动评分证明游戏好玩。

## 从已有目标开始

先读项目 brief、当前构建、玩法决定和试玩问题。提取玩家做什么、为什么做、可用信息、可选行动、代价、结果及成功/失败后的去向。用户已定的玩法直接深化；缺少的实现细节可以记录假设继续。只有会改变核心体验的冲突才集中提交选项，不重新盘问整份问卷。

## 设计与验证闭环

1. 明确本轮问题，例如“探索是否有可理解的发现与回报”“几种战术是否有真实取舍”。把想达到的体验与现有证据分开。
2. 按[设计分析方法](references/design-methods.md)选有用的视角：核心/会话循环、MDA、信息与风险、规则组合、进度或资源流；任务/对白、关卡节奏、教学与内容扩展需要时读同页的[内容检查](references/design-methods.md#内容关卡叙事与教学)。不要对每个小功能套全部框架。
3. 写清规则和状态边界，包括输入条件、可见反馈、例外、失败、重试及保存。关注实际选择与行动，不将“加等级、奖励或敌人”当通用答案。
4. 对关键不确定性提出最小可逆变体。记录预期行为、与基线的差别、观察方法以及什么结果会推翻假设。多项改动有依赖时注明，不用无法归因的大改掩盖问题。
5. 制作请求继续在所选引擎实现并试玩。先用灰盒或已有内容验证，再扩展正式资产。分别保存运行观察、玩家反馈、推测和未验证项；不存在玩家测试时直接说明。
6. 根据结果修改规则、表达或参数，将已确定的决定回写项目，并检查受影响的教学、UI、关卡、存档和资产。功能通过与用户认可体验分别记录。

简单问题在项目现有 brief/任务中记录即可；需要多轮实验时可用[设计假设模板](assets/design-hypothesis.md)，不强制维护额外 GDD。

## 与本机制作链衔接

- 全项目阶段、Web/Unreal选路及实现由 [Game Production Workflows](../game-production-workflows/SKILL.md) 编排。Web继续调用 Game Studio；Unreal继续使用已连接的 Unreal 技能。此模块不另建一套引擎或 Agent 团队。
- 玩家读不懂信息、找不到操作或菜单阻断时，配合 [Game UI Design](../game-ui-design/SKILL.md)；视觉语义、风格与辨识配合 [Game Art Direction](../game-art-direction/SKILL.md)。
- 操作手感也包括输入响应、运动、镜头、碰撞及动画时序。反馈层可以加强声音、特效或适度停顿，但不能替代正确规则与控制。强度由类型和用户意图决定。
- 分析请求交付设计结论与验证办法；已授权制作则继续完成实现、运行检查和修复，不停在设计文档。

## 使用边界

MDA中的 Aesthetics 指玩家的体验与情绪目标，不能只理解为画面美术。Bartle、flow、奖励与动机模型可帮助提问，不能据此给个体贴标签或推导通用留存保证。短循环时长、成功率、奖励频率、动态难度都按项目确定，不套固定阈值。解谜、叙事、沙盒与策略不必都变成即时奖励循环。
