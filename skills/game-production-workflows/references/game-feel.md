# 操作手感与反馈打磨

从灰盒开始建立控制基线，在垂直切片中确定代表性反馈，再用于后续内容和打磨。适用于移动、落地、拾取、建造、点选、命中或菜单操作等实际行为；不把所有游戏都改成强震屏、强闪光的动作游戏。

## 先定位问题，再决定改哪一层

沿“输入 → 规则/物理结果 → 动画与镜头 → 音画/UI反馈”观察当前构建，区分响应慢、控制不准、接触不对、反馈不足和画面卡顿。已有用户认可的规则与表现保留，只调整本轮相关变量。

| 问题 | 处理位置 |
|---|---|
| 输入丢失、起停/转向不合意、碰撞或命令不准 | UE的[控制与交互](unreal-implementation.md)或已选Game Studio运行时；先查焦点、时序、运动与判定 |
| 滑步、手脚接触、动作过渡或释放帧不对 | [角色与动画](character-animation.md)；必要时回Blender修动作，再接入运行端 |
| 行为正确但显得轻、弱、缺少层次 | 按下节组织事件反馈，协调[音频与界面](presentation.md)和[视觉效果](levels-and-visuals.md) |
| 只在远端、低帧率或密集场景下变差 | 分别查[联机](multiplayer.md)或[性能](quality-performance-release.md)，不能单靠加强特效解决 |
| 行动缺少意义或规则不好理解 | 回到`game-design-theory`或`game-ui-design`，反馈打磨不替代玩法与信息设计 |

输入缓冲、离开边缘后的跳跃容错、瞄准辅助和动作取消窗口按类型与用户意图选择。它们可能改变难度、规则或公平性，不作为所有项目的默认改动；时间窗用实际时间表达并检查帧率影响。

## 为代表性事件建立可复用配方

1. 选一段能反复操作的场景，记录当前构建、输入、帧率/设备和具体问题。先测核心行为，不同时替换控制、动作、镜头和美术。
2. 明确事件的条件、真实结果及起始/接触/恢复时点。将“尝试使用”与“已成功使用”分开；同一次拾取或命中不能因多个回调重复扣资源或触发反馈。
3. 按需要组合动画、音效、粒子/材质、相机、UI和设备振动等通道。确定各通道负责传达什么、何时开始/结束、强度及打断/叠加规则；用少量可复用的重要性分级保持全局一致，不规定所有事件必须具备同样通道或固定毫秒数。
4. 先对齐真实接触、行动结果与声音，再调缓动、短暂停顿、镜头响应和细节。第一人称注意瞄准与晕动，第三人称注意跟随与接触，俯视注意点选、群体可辨识性和命令反馈；不能用大特效遮住下一次决策。
5. 反馈施加到适当的显示层。相机震动不移动碰撞体，视觉缩放不暗改命中范围；真实击退、位移或伤害由玩法/物理层处理。短暂停顿使用可恢复的时序，检查输入缓冲、连续触发、暂停/退出及恢复，避免阻塞主循环。
6. 联机时区分可预测的本地表现与权威确认的结果；确认、重放和校正不能重复播放同一事件。不要为本地打击感直接暂停服务端或全局世界；同步与异常处理按[联机分支](multiplayer.md)。
7. 将选定参数放进已有项目配置/数据或等价记录，记录版本、适用事件与保留的规则。先在第二个对象或场景复用成功，再批量扩展。

## 执行与结果回接

UE由已连接的Unreal执行层处理控制/动画、相机反馈、Niagara、音频和UMG等适用系统；Web继续交Game Studio的既定运行时与UI技能。缺少动作/音画素材时才调用已有Blender或ComfyUI分支，使用同一项目与资产ID；不为效果调参重做全部资产。方法不绑定Godot/Unity示例或新的独立Skill，具体接口由执行层按当前工程确定。

交回本轮问题与原因、实际修改对象/参数、代表性事件配方、对输入/规则/性能的影响、测试证据和待评审项，写回已有简报/状态。已授权实现继续运行、修复并接回当前阶段，不只交一份“手感建议”。

## 验收

- 同场景、相近负载与输入做基线/变体对照，检查响应、因果与可读性；主观偏好由实际可玩结果或录像评审，不凭特效数量判好坏。
- 连续操作、同时触发、打断、暂停/恢复、窗口失焦和重试后，检查输入仍有效、反馈能结束、相机/材质/时间状态能恢复。
- 在目标设备与代表性帧率下检查，联机还看远端观察者、预测被拒绝和校正；不能只验证主机画面。
- 按需要提供减少晃动/闪光、振动强度等选项，并验证实际生效和设置恢复；同时检查重要声音/UI提示不会被覆盖。
- 检查事件密集时的帧时间、音频/特效并发和资源回收，再按[质量与交付](quality-performance-release.md)接回正式构建验收。
