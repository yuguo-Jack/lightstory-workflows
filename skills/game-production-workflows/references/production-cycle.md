# 制作阶段与推进规则

阶段名称可合并，依据项目风险和规模选择；不要变成必须产生大量文档的审批链。始终区分“证明玩法”“证明品质和生产方法”“批量扩展内容”。

| 阶段 | 要解决的问题 | 最小可审阅产物 | 执行路由与继续条件 |
|---|---|---|---|
| 概念与可行性 | 做给谁、玩什么；选择Web/UE并判断资源 | 简短 brief、运行路线/理由、参考职责、范围与风险 | 按需调用设计/美术模块；确定运行入口与关键技术的验证办法 |
| 灰盒原型 | 控制、镜头、规则、目标是否成立 | 可操作的小关卡；代表性输入与反馈 | 设计/UI要求交Game Studio或Unreal执行，能完成一次核心循环并识别缺陷 |
| 风险试验 | 最可能推翻方案的环节能否实现 | 如近景脸部、斗篷碰撞、成群单位、联机的最小测试 | 只调用有关资产/角色/运行端分支，取得真实证据和可行替代 |
| 垂直切片 | 目标品质能否串通、重做一次是否仍可用 | 少量最终质量资产＋玩法＋音画＋UI＋打包构建 | 美术/UI定标，Comfy/Blender按分工产物回接运行端；真实镜头品质/性能及复用成立 |
| 功能与内容生产 | 如何有节奏地完成约定规模 | 可复用模块、资产队列、关卡/任务增量 | 执行技能逐批制作并回接，按版本/依赖验收，不堆积未导入素材 |
| 整体打磨 | 内容是否完整、一致且易理解 | 核心路径完整，教学、恢复、反馈和过渡齐全 | 按缺陷回到玩法/UI/资产/运行端；整段视频交Video完成后接回；主观反馈已处置 |
| 稳定与交付 | 脱离开发环境是否还可玩 | 独立构建、测试记录、使用说明 | 运行端专项测试/性能与正式构建完成约定路径，许可和资源满足目标 |
| 更新与维护 | 如何修复而不破坏旧成果 | 可回退版本、变更范围、针对性回归 | 按变更依赖重测必要存档/资产/路径，保留可用构建 |

“完成一次核心循环”不默认必须战斗。例如探索可以是发现线索、使用物品、解开阻碍并得到反馈；经营可以是决策、消耗、产出、扩展。用户未选择类型时不先塞枪械或敌人。

先按[runtime-selection.md](runtime-selection.md)选运行路线，再分配资产制作。Web实际进入Game Studio执行链；UE进入Unreal执行层。阶段目标相同，但Web以正式浏览器构建/试玩验收，UE以原生打包/实机验收，不给Web套用PIE/UAsset/Shipping前置条件。

## 设计模块怎样进入阶段

- **概念与灰盒**：需求有玩法不确定性时调用 `game-design-theory`，选择可验证的问题与最小变体；同轮继续在既定运行端实现。用户已有清晰规则时直接执行，不额外套理论分析。
- **视觉切片与UI原型**：需要审美定标时用 `game-art-direction`，将已选参考转为项目规范；用 `game-ui-design` 确定适用屏幕/状态和输入流。视觉切片包含真实游戏镜头，UI原型包含真实状态与可操作路径，再扩展正式素材。
- **操作手感**：灰盒先定位输入、控制与接触问题，切片按[手感分支](game-feel.md)确定代表性事件的反馈配方；后续内容复用并按影响回归，不等美术全做完才第一次调手感。
- **在线项目**：概念/可行性阶段按[联机分支](multiplayer.md)明确拓扑、状态归属与恢复；灰盒跑通多实例共享交互，切片检查表现与同步，生产和交付继续覆盖目标负载及异常网络。单机/同屏不套完整在线后端流程。
- **批量生产与打磨**：沿用同一组玩法决定、美术规范和UI语义；出现问题按症状回到对应模块，只改相关范围。视觉/交互提案不算游戏端验收通过，模板完成也不算玩家体验通过。

## 执行粒度

用一项可观察变化作为一轮：目标 → 现状 → 最小改动 → 编译/导入 → 运行 → 核对证据 → 修复 → 保存。一次素材批量或场景编辑要有对象范围和恢复点。通过的检查不因进入下一阶段无理由全部重跑，新增改动按影响范围回归。

每批产物核对后，按[周期空间管理](project-operations.md)处理确认无用的大临时文件再扩展下一批；连续工作至少每2小时检查，增长/低空间预警提前触发。阶段结束与暂停/交接前保存存储记录，活动任务和必要返工缓存保留，不为清理制造整份大备份。

自动化承担脚本、工程、生成、检查与返工；玩法是否有趣、美术是否贴近个人理想，需要参考与评审。将“现在需要选择的决定”与“可以继续完成的实现”分开。已授权的普通本地操作继续执行；新增付费服务、发布、购买或破坏性替换不由方法论自动授权。

## 控制范围和返工

- 每个需求保留：用户意图、可玩行为、所需内容、验收方式、依赖，不只列引擎功能名。
- 优先打通一条用户能玩的路径，同时保留完整项目清单。精美展示房间不能替代用户要的游戏。
- 扩充 20 个角色前先把第二个角色走通，检查是否依赖第一个角色的名字、固定尺寸或手工位置。
- 原型允许占位；正式交付逐项处理占位素材、失效按钮、未接音效、调试 UI、假存档和未完成分支。
- 联机沿上述分支在早期做风险试验；VR、开放世界、程序生成和大群体 AI 也先验证最可能推翻方案的环节。

阶段结束只记录支持续作的事实：当前可用构建/提交、已完成内容、未解决问题、已确定决定、需要用户判断的结果、下一轮任务。阶段推进依据证据，不按文档数量或素材数量计算完成度。

参考：[GameDevFoundry 制作阶段](https://www.gamedevfoundry.com/StagesOfGameDevelopment.html)。以上执行粒度针对本机方式调整，不要求所有项目使用相同阶段名称。
