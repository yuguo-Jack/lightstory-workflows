# Pika H3 Flex：本机六步生成分支

用于文/图生视频、多参考创作和视频编辑等镜头制作。它是 Pika 对 H3 的后训练与少步蒸馏适配器，作为现有常规 H3、Turbo 之外的可选路线。满足本次审片要求时可直接用于正式成片，不要求再换普通 H3 重做。任务素材、导演台、外部 Group、生效优先级、导出与返工沿用 [H3 说明](h3.md)。提示词仍用 `$h3-prompt-writing`。

本页W指`${LIGHTSTORY_ROOT}`；正式模型、输入和成品仍使用ComfyUI原生目录，具体位置与启动见[运行参考](runtime.md)。

## 优势场景与路线选择

三条路线并列选用；普通版的通用制作、专项动作/运镜、后处理及项目接续优势见[普通H3与三路选择](h3.md#普通h3的优势与适用场景)。本页集中维护Flex差异，不据此降低普通版的选用优先级。

**Flex 的主要价值是较好的出片效率与画面表现，并非只有少步加速。** Pika 在 H3 上进行了美学数据微调、六步蒸馏和奖励/偏好优化。作者评测报告的相对优势包括：文字/图片生成中的人体表现、复杂构图与音画同步，以及参考生成中的视觉风格、取景与运镜。这是作者在其对照模型/数据上的结果，本机量化链路没有重复该完整基准。[官方技术报告](https://pika.art/blog/pika-h3-flex-research)

**官方展示的应用**包括复杂运镜、多镜头叙事、商品广告、风格化动画、多参考组合、动作迁移、人物/物体替换和局部视频编辑。这说明应用覆盖广，不代表每项都已取得对比领先，也不代表本机已逐项验证这些复杂案例；选路不局限于人物、生活或广告。

**作者报告的相对弱项**包括物理、多场景叙事、光照材质，以及强动作或控制视频参考任务，其他参评模型在这些方面仍有优势。能展示多镜头/动作迁移，与多场景叙事或动作控制对比领先是不同结论。高要求镜头先做代表样片比较，必要时接Blender预演或确定性CG/合成；不把该评测直接解释为普通H3在这些方面全部优于Flex。应用展示与比较结论均来自上述官方技术报告。

| 目标镜头 | 建议选路 | 理由与边界 |
|---|---|---|
| 人物对白、日常生活、温和表演 | 先试Flex | 本机人物挥手、对白和连续动作已出片；中英文ASR吻合，但音色、口型与表演细节仍逐镜审查 |
| 商品展示、广告、美术风格明确的动画/短片 | 先试Flex | 后训练针对美学、清晰度和真实感，适合较快探索视觉表现；商品形状、商标、文字不能由此视为精确保留 |
| 复杂运镜、多镜头叙事、动作迁移 | Flex可参与选路，先试代表镜头 | 官方有应用展示；复杂编排、跨场景连续性和动作准确度仍逐镜检查，多镜头由导演台/剪辑组织，不视为比较领先或本机全场景已测 |
| 常规首帧/首尾帧、主体参考、简单视频编辑 | Flex可作为首选尝试 | 本机端点、混合参考和杯子换色已验证；复杂参考仍可能偏离指定姿态，必要时与普通H3对照 |
| Combat/Repair/兵器等专项LoRA，或二采、放大、修脸组合 | 优先普通H3现有配套 | 本机这些组合的验证更完整；不是已证明普通H3对所有动作、物理或材质都更好。Flex叠加组合需另核对 |
| 大量构图/提示词/参考方案试拍 | 按素材选择Turbo或Flex | 本机Turbo为FL2VA八步、Ref2VA四步；Flex六步。参考编码、上下文和每步计算量也影响时间，不能仅按步数排速度 |

本机同条件480p单例为普通H3约179秒、Flex约65秒，约2.75倍全流程速度比；尚无同条件三方画质排名。其他题材先做一个代表镜头，再决定批量路线。不要把“25步”直接等同于画质更高，也不要默认所有正式镜头都应回到普通H3。

三条路线都可通过导演台生成连续镜头；连续性仍依赖锚点、动作/运镜承接和段间引导，未证明Flex一定更连续。独立分镜可分别选路线，同一连续链尽量保持配套一致。少步主要节省采样时间，不使峰值显存/物理内存按步数同比下降。

## 已部署文件与固定采样组合

复用对应的 `minimax_h3_fl2va_pruned_w6a8` / `minimax_h3_ref2va_pruned_w6a8`、`qwen3vl_32b_minimax_h3_nvfp4_awq`、H3 INT8 视频 VAE、FP32 音频 VAE。新增文件在原生 `models/loras`：

- `pika_h3_flex_fl2va_v1_bf16.safetensors`：文字、首帧、首尾帧及 FL2VA 连续生成。
- `pika_h3_flex_ref2va_v1_bf16.safetensors`：图/音/视频参考及源视频编辑。

两份合计 3,912,344,608 字节，来自官方 Comfy-Org 转换仓，固定修订与官方 SHA256 在 ${LIGHTSTORY_ROOT}/models/weights.lock.json；不下载整个 Pika 仓库或重复保存底模。

文件名中的 BF16 指这两份适配器，底模仍是 W6A8。本轮验证量化链路兼容性和实际输出，未验证它与官方全精度底模的数值/画质等价。

接线与参数必须配套：

```text
对应家族 UNET → LoraLoaderModelOnly(Flex, strength=1.0) → Director.model
ManualSigmas → Director.sigmas
Director: sampler=lcm, cfg=1, shift_video=12, shift_audio=3
ManualSigmas: 1.0, 0.972973, 0.923077, 0.8, 0.571429, 0.333333, 0.0
```

这是六次采样迭代。外接 SIGMAS 后导演台的 steps / scheduler 下拉不决定一采噪声表，sampler 下拉仍有效。保留 `lcm` 和连接，不能只把常规画布改成六步，也不能替换为六步 Euler。新模板已设置这些内容。

少步来自模型后训练/蒸馏，不是更换注意力内核。本轮仍复用现有 PyTorch attention 启动配置，未为Flex另装SageAttention或FlashAttention包。

**不叠加 Turbo / Lightning。** Combat、Repair、运镜等专项 LoRA 与 Flex 的交叉组合没有沿用旧 H3 的通过结论，按任务需要单独比较，不默认加。不要为了更快而把官方六步表截短。

## 功能入口与使用

在 ComfyUI 工作流浏览器打开 `MiniMax H3/Pika Flex/<功能>.json`。API 位于 ${LIGHTSTORY_ROOT}/workflows/api/MiniMax H3/Pika Flex；使用 `library.py list/show/prepare` 可按完整模型/功能名查询和创建任务副本。

| 功能 | 编辑入口与用途 |
|---|---|
| `01_文生视频` | 导演台实际生效的全局/段提示；生成画面及混合音轨 |
| `02_首帧生视频` | 替换 LoadImage；在 ImageToVideo Group 修改提示和时长。起点是竖幅 544×800 |
| `03_首尾帧生视频` | 替换两端图片，Group 描述过渡；可断开首端或尾端成为仅尾帧/仅首帧，删除未使用支路 |
| `04_多模态参考生视频` | 默认两图＋动作视频＋独立音频；在 ReferenceToVideo Group 编辑职责和标签；不需要的输入断开并移除对应标签 |
| `05_源视频编辑` | 在导演台内替换示例源视频、范围和编辑指令；Ref2VA，自动绑定源片段为 `<Video 1>` |
| `06_连续长镜头` | 内部两段、各约 5 秒，段间引导开启，22 帧上下文；后段“引用上段”开启 |

### 从打开画布到导出

1. 按[运行参考](runtime.md)检查或复用8188服务、空队列、Balanced配置和内存余量；8192只展示说明/结果。UI打开上表的`.json`；程序执行读取对应`.api.json`，不要把两者混用。
2. 另存任务副本，设置独立输出前缀和`cache_name`。固定seed用于同条件比较；选片/批量变体可改种子并保留记录，seed不能锁定人物，也不保证切换路线/尺寸后重现原构图。
3. 替换本次全部素材与提示词，不能留下无意使用的示例。02/03/04连接外部Group时，修改Group中的prompt、duration_sec和输入；01/05/06检查导演台实际生效的global/segments。API须同步完整timeline_data，`library.py prepare`只准备副本，不会提交推理。
4. 保持对应底模家族、Flex适配器强度1、LCM、CFG1和外接六步表配套；改变强度/噪声表属于新的生成配置，不能当成已验证的风格按钮。调整输出尺寸、时长和参考数量时按下节检查；从约480p/5秒的代表镜头开始，需要时再用已测768p配置。
5. 保存并Queue；程序执行按[提交与验收](runtime.md#提交与验收)提交`/prompt`、记录prompt_id并查询真实history。一次只跑一个重GPU任务，提交超时先查队列，避免重复排队。
6. 从history定位实际MP4，检查完整解码、实际尺寸/FPS/帧数、有效声音和画面内容；首尾帧对照端点，参考编辑核对保留项，连续镜头检查接点前后画面/声音。音轨存在或ASR吻合不代替试听和口型检查。
7. 成品默认在共享output的`MiniMax H3/Pika Flex`下；任务副本可用自己的前缀。保留可编辑工作流、素材关联和参数记录。完整影片的配音/配乐、剪辑、包装及交付继续由`$video-production-workflows`统筹；交付后按[清理规则](cleanup.md)处理无用途的本任务缓存。

输入均为可替换示例，不识别固定文件名、人物或项目。新图片可先由 [Qwen](qwen.md) 制作/编辑并筛查一致性；首尾关键帧、主体参考与动作/构图视频分工明确。Ref2VA 参考是生成条件，不是像素、骨骼或相机轨迹的硬锁。

多模态样例的中文正文ASR吻合，但人物后半段仍转成明显侧身，没有严格保持“mostly front-facing”。遇到姿态冲突先移除/替换动作视频，只保留身份图确认主体，再逐一补声音和运动条件；不要因为全部端口能跑就默认所有参考约束同时满足。

**Director Group 的 API 输入从 0 编号**：第一图为 `ref_images.ref_image_0`，第一视频为 `ref_videos.ref_video_0`，第一独立声音为 `ref_audios.ref_audio_0`；提示中的标签则从 `<Picture 1>` / `<Video 1>` / `<Audio 1>` 开始。不要照抄其他节点的端口编号，也不要靠自动补标签掩盖错位。本分支已修正继承模板的此问题；输入视频的配对音轨与独立声音分别检查。

横幅起点 864×480，竖幅 544×800，24fps、batch1、每段 124 帧，约 5.17 秒。模板用固定画幅，使界面与 API 一致；换素材后按其比例调整导演台输出宽高或选择最长边缩放，检查预览和实际导出尺寸，避免裁掉头脚。宽高按 32 对齐。API 调整时同步顶层 width/height/ref_max_size、timeline_data 对应字段及 output，Group 时长才是外部输入模式的有效时长。

官方单段请求时长为5–15整数秒，原生帧桶为17k+5；不能把该范围和参考数量上限当成本机所有组合的实测。官方Ref2VA配方要求至少一张图片或一个视频，上限9图、3视频、3份独立音频且总计不超过12份；每个视频/独立音频为2–15秒，全部参考视频的时长之和、全部独立音频的时长之和分别不超过15秒。视频内嵌原声不额外算一份独立音频。以[官方公开配方](https://github.com/Pika-Labs/Pika-H3-Flex)为使用依据；本机节点允许的范围可能不同，不等于全部已测。增加输入前检查RAM/显存余量。

### 参考素材、提示与声音

- 关键帧先检查主体是否清楚、两端比例和对象是否对应；有意跨场景切镜时分开生成，避免要求首尾帧将不相干场景变形连起来。固定画幅会裁切时，按目标比例补边/重构图或使用合适的缩放方式；不要拉伸人物。
- 当前04通过`GetVideoComponents.images → Group.ref_videos`只传视频帧，没有传源FPS。不同帧率的动作参考先在任务目录制作24fps副本并核对时长，避免逐帧被当24fps解释而改变速度；原件保留。导演台内部上传视频走另一条读取路径，也要检查实际范围和速度，不机械假定等价。
- 当前04没有把参考视频内嵌声音接成视频配对音轨，声音来自独立音频支路。需要视频原声时另核对配对音频输入和有效标签；“视频配对原声＋独立声音”的全部组合未在本轮验证，不照搬官方CLI自动保留内嵌音轨的行为。
- 用`$h3-prompt-writing`按文字/关键帧或Ref2VA格式组织提示。写清身份/服装/光线锚点、一个可发生的动作过程、相机方向及声音职责；台词长度匹配本段时长。明确无对白/无音乐的要求，导出后仍检查。
- 音频参考用于影响生成，不保证逐样本复制，也不等于专业音色克隆。必须精确保留已有配音/歌曲时，在后期复用原音或Ming/Music成品并对齐，替换声音后重新检查口型/节奏。参考视频的音轨、声音参考、生成音轨和后期主轨分别登记。本轮MP4音轨为32kHz立体声AAC混合轨；项目后期可按交付要求转48kHz，不将转采样声称为原生48kHz。

## 连续性、切换与后处理

- 同一 Director 的采样器和噪声表是全局的。用 Flex 连续生成时，两段保持同一底模家族、Flex、噪声表、画幅与 FPS；不能在中间段撤掉 Flex 却继续使用全局六步。
- 常规 H3、Turbo 与 Flex 是不同采样路线。跨路线改版使用新 cache_name，重新生成目标镜头及受影响的连续后段；同种子不保证重现同一人物和构图。需要承接时用确认的首帧/参考和运动上下文。
- 原有段间引导可以传递运动/声音上下文，但依然可能发生身份、动作、曝光和声音跳变；检查接点前后数帧，不以总帧数或“引导已开启”代替审片。缓存与分组 LoRA 边界见 [搭配说明](h3-lora-continuity.md)。
- 模板将 `cache_frames_codec` 设为 `ffv1`，为段缓存使用无损压缩，减少磁盘占用但增加编解码成本；这和启动器的节点 `cache-none` 是两套缓存机制，任务结束仍按用途清理。
- 原来的二采、修脸、语义桥、潜空间放大及 SelfLift **不是已验证的 Flex 全组合**。SelfLift 要求 Euler，与本分支的 LCM 路线不同。Refine 未接独立 refine_model 时会继承 Flex，不能直接套原常规二采的步数/调度。需要后处理时按其模型与噪声表单独配置验证，或选择已验证的常规 H3 后处理路线。
- 托管服务的 1080p/2K/4K 增强、五路分离音轨和在线提示词服务不在公开本地权重内；本机导出的是混合音轨。旁白/音乐仍可由 Ming/Music 单独制作再剪辑混音。

## 本机证据、排错与清理

历史摘要见[验证记录](../../../docs/evidence/historical-summary.json)，逐画布状态见工程`workflows/catalog.json`。额外768p、仅尾帧和普通H3对照按实际结果区分，不因官方支持就宣称新环境通过。历史H100/B300速度不是RTX4080端到端耗时。

六项基础画布已在本机执行并完整解码：文字约65秒、首帧69秒、首尾帧91秒、两图＋视频＋独立声音217秒、简单源片换色187秒、两段连续159秒。单段124帧；连续实际260帧/10.83秒，接点附近120–128帧已检查，未见明显硬切/换脸，但有轻微纹理/位置变化。中英文明确对白的ASR均与目标正文吻合；不冒充主观听感、音色或逐帧口型认证。复杂参考比纯文生更慢，不按“六步”推算统一耗时。

补测仅尾帧约67秒；文生1344×768、124帧约205秒，英文ASR吻合。该768p例最低可用物理RAM约10.38GiB，未触发保护；尚未验证768p多参考/15秒。要复用此画幅，在01的任务副本中同时将Director宽高/ref_max_size设为1344/768/1344，并同步timeline_data的width/height/refMaxSize及output宽高/longEdge。不用更改LCM六步表。

同条件普通H3 25步约179秒，对应Flex六步约65秒，本例全流程速度比约2.75。两者构图与色调不同，不能把单种子对照当成全题材质量排名。六基础＋普通对照＋两项补测共九项执行完成，本轮最低可用RAM约7.68GiB；使用的参考数量、片长和资源压力不可外推。

出现六步不生效，检查外接 SIGMAS 连接和实际 Director 报告；LoRA 失败检查对应家族、文件和 `208 patches attached` / 未加载 key 日志。需要恢复普通 H3 时，换回原画布或同时移除 Flex 与外接表、恢复常规采样配置。原常规模板继续保留。

| 现象 | 优先检查与处理 |
|---|---|
| 仍生成旧提示/旧人物，改时长没生效 | 外部Group与内部时间线的优先级；同步实际生效的提示、素材、duration_sec/帧数，并确认没有命中旧项目缓存 |
| 六步画面异常或Flex效果未生效 | 对应家族的底模/适配器、强度1、LCM、CFG1、ManualSigmas连接和实际六步报告；检查是否误叠Turbo及未加载的LoRA key |
| 模型下拉找不到文件 | 检查正式实例、原生loras路径、文件是否已完成校验，再刷新列表/重载画布；不先整体重装环境 |
| 被裁头脚、比例变化、动作参考忽快忽慢 | 输出模式/宽高与输入比例、参考FPS、有效裁剪范围；先修正素材和尺寸，不用提高步数补救 |
| 多参考揉合、姿态/物体关系偏离 | 减少相互冲突的参考，一次明确身份、动作或风格职责；先确认少量参考有效，再逐项加入；精确轨迹/接触可改用可控CG或后期合成 |
| 台词截断、声音不对或近静音 | 检查台词与实际时长、参考音频接线/标签、生成/原声/静音模式及真实波形；必要时缩短台词或另做配音，不把ASR当听感认证 |
| 导出比计划长或部分段不见 | 帧桶、保留完整生成、选择运行、全部/分段导出及实际缓存；按最终帧数剪辑，不用再次盲生成来凑时长 |
| CUDA OOM或内存保护中断 | 按[运行排错](runtime.md#失败处理)区分显存、物理RAM和提交余量；减尺寸/参考数量/单段时长，串行执行并保留保护。分页不增加物理RAM或显存，不通过减六步表硬扛 |

每批完成后遵守 [清理规则](cleanup.md)：成片完整解码、无续作/返工需求后，清理本任务在 ${STATE_ROOT}/runtime/cache/h3 的段缓存、废弃输出及已无断点恢复用途的下载残留；未完成且仍要续传的`.part`和状态保留。保留Flex权重、底模、原始素材、成品及小型证据；仅本次验收的临时语音识别模型确认不再使用后可清理，不是正式工作流依赖。
