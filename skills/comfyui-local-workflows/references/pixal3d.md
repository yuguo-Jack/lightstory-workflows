# Pixal3D 使用参考



以下包含2026-10-29部署版本的操作与历史实测边界。验证素材不是用户输入，执行时读取当前API和节点接口。



## 4. Pixal3D：图片到可编辑GLB与材质



### 4.1 操作顺序与输入要求



1. 检查主体抠图与居中，头发、手指、鞋尖和配饰不可被裁掉。各建模画布已包含相应预处理，不必先额外跑一遍`00_主体抠图与居中`；00是四路预处理预览/保存工具。只有一张图时直接用单图画布，或在任务副本保留所需预处理分支，不让其余槽位无意处理旧示例。

2. 打开 `01_单图建模_1024`，替换正面输入，运行后转动检查正面、背面、侧面。

3. 背面不可靠时，用 `03_双视图建模_1024` 加入一致的背面；多图不是自动提高颜值的开关。

4. `05_四视图建模_1024` 槽位是 **front / left / back / right**，按主体自身左右方向一致放置。侧面应约90°，姿态、比例、配饰必须一致。

5. 单图、双图、四图的1536高级版本分别是 `02/04/06`。先用1024筛选输入，再检查1536是否确实改善细节。

6. 合格结果导入Blender修形、检查拓扑。动画另需重拓扑、骨骼、蒙皮；引擎使用另需碰撞体和性能优化。



多图预处理分别按每张主体长边裁切缩放。宽扁物体或侧面轮廓长度差异大的物体可能因此失去一致的投影尺度；先人工对齐尺寸与中心，必要时使用同尺寸黑底方图绕过独立裁切，直连条件节点。没有自动校准多张照片相机或纠正不一致服饰的步骤。



### 4.2 画布步骤、参数与必需节点



BiRefNet抠图 → 蒙版裁切居中 → DINO/NAF视觉条件 → 稀疏结构与形状级联 → 几何解码 → UDF/QEF表面重建 → 简化、平滑法线 → UV → 纹理生成与PBR烘焙 → GLB及独立贴图。



| 参数 | 1024版本 | 1536高级版本 |
|---|---|---|
| 主体预处理 | 1024方图，pad_factor 1.1 | 同左 |
| 形状生成级别 | 1024 | 1536 |
| 表面重建 | 768、平滑6次 | 1024、平滑6次 |
| 目标三角面数 | 350,000 | 600,000 |
| 纹理 | 4K PBR，独立AO 2K | 同左 |



重建、平滑可能改变细带、发梢、手指。`drop_small_components=0`避免主动删除小连通部件，但不保证它们一定生成成功。4K尺寸也不等于每个像素都有真实新增细节。



单图使用独立权重、MoGe估计FOV；多图使用独立多视图权重，默认FOV20°，有透视的参考图应检查相机。匹配FOV也不等于完整匹配相机：原生单/多图还有距离和特征融合机制差别，不能把结果差异完全归因于图片数量。



Pixal各阶段使用配套单/多图模型、DINO/NAF条件及形状/纹理VAE；TRELLIS2组件名属于配套实现，不替换成Qwen图像VAE。结构、形状、纹理的采样与`CFGOverride`分别生效，不把一个KSampler的CFG当成全流程统一强度。当前模板无默认美化/动作LoRA。



保留以下两个通用自定义节点包，均没有人物、文件名或项目专用规则，也没有改ComfyUI核心文件：



- `custom_nodes/ComfyUI-MeshUtilities`：`UnwrapMeshPreserveNormals`在UV拆点时传递平滑法线，减少接缝裂光。

- `custom_nodes/ComfyUI-Pixal3DMemory`：低内存单/多图条件、形状/纹理解码节点。NAF保持后端原生计算精度及512/1024空间分辨率，改用临时文件映射；注意力按独立空间单元二维分块，解码前释放采样模型。`dino_v3_L_naf_fp32`是权重文件名，不代表后端始终按FP32计算；本轮官方输入的日志记录为FP16特征。采样步数、主权重量化、几何级别、4K纹理保持既定值。



临时映射峰值约单图3GiB、双图6GiB、四图12GiB，位于本后端临时目录，任务结束回收。九次任务后映射文件均已释放。64MiB小规模测试验证Windows生命周期，CPU/CUDA分块计算四项对照最大误差均为0；这是这些注意力用例的数值检查，不是对全部大型张量逐元素证明。更新ComfyUI后需重新核对依赖的原生接口。

### 4.4 查看、比较与继续编辑



- `Save3DAdvanced`预览并保存GLB，位置由 `filename_prefix`决定。输出在共享 `output/Pixal3D`。

- GLB内嵌BaseColor、ORM（AO/粗糙度/金属度）、Normal，并另存PBR贴图。Blender用“文件 → 导入 → glTF 2.0”，在材质或渲染模式审查。

- Unreal导入后核对材质、法线、单位和碰撞体。默认35万/60万面的静态网格通常还需优化，不能直接当成熟动画游戏资产。

- UV法线连续不等于网格无孔、无非流形边；眼睛、手指、薄面、穿插仍需人工审查，默认没有骨骼、蒙皮或服装物理。



[修复后单/双/四图及同FOV对照](../../../docs/evidence/historical-summary.json)采用原Qwen人物图、同灯光和相机，未经眼部或材质人工精修。本轮精确API、日志、资源采样和结果在 `validation/Pixal3D/repair-20261029`；旧失败记录保留为历史，已由本轮修复结果取代。执行通过、格式检查通过和最终模型美术质量是不同结论。

### 4.5 32GB内存：推荐启动方式与保护中断的处理



**复杂新输入推荐 `Balanced` 启动配置，并保留自动内存保护。** 该配置使用ComfyUI原生PyTorch注意力、预留4GB显存、关闭节点缓存，启动脚本同时启动内存管理进程。`PixalStable`是前述人物样本的历史验证配置；其中的分块注意力在官方复杂机甲1536测试中曾达到每步约80秒，不把旧人物样本的耗时当作任意新输入的性能保证。



按[服务与配置切换](runtime.md#服务和内存)等空队列后选择Balanced，避免重复启动共用数据库的后端。从1024开始逐个运行；单/双/四图各自的验证范围不能混作同一结论。



**为何有映射文件和分页文件，仍会触发物理内存保护？** 当前四图的中间视觉特征映射约12GiB，文件映射被读写时仍会驻留在物理内存；后面还叠加形状、网格、UV与4K贴图的临时张量。`/free`释放模型不等于Python、PyTorch和文件映射的全部驻留页立即归还。官方机甲补测的两次中断，分别在可用RAM约1.63GiB和2.47GiB时发生，当时提交内存仍有约25GiB以上余量，属于物理内存压力，不是分页额度用完。32GB不能据此宣称所有复杂四图输入都宽裕。



自动处理采用两层策略，均不修改模型数值、采样参数、参考图数量或纹理尺寸：



1. **提前回收驻留页。** 仅当正在运行Pixal3D、可用RAM低于8GiB且提交余量至少10GiB时，内存管理进程核对本安装的后端PID、父子进程和当前任务，再调用Windows `K32EmptyWorkingSet`。分配和数据保留，Windows按需从映射文件或分页文件读回；这可能增加磁盘I/O、使任务变慢，不是释放仍在使用的张量。

2. **继续保留原来的硬保护。** 可用RAM低于2.5GiB或提交余量低于6GiB时，仍中断当前生成，避免桌面卡死。不会因为已尝试回收就忽略保护。非Pixal模型保留原有保护逻辑。



该自动回收是本工作目录启动管理器的功能，**不在JSON画布内部**。只复制画布到别的ComfyUI安装、直接用Desktop另起后端、退出内存管理进程，都不能假定仍有相同保障。它只操作核对成功的本机托管进程，不会回收浏览器、其他应用或无法确认归属的Python进程。



| 实际问题 | 如何确认 | 处理顺序 |
|---|---|---|
| 物理RAM保护中断 | `runtime/memory_guard.json`中的`last_interrupt.prompt_id`与失败任务一致，`available_RAM_GiB`低于2.5 | 等队列清空；确认Balanced及`residency_reclaim_enabled=true`；关闭确实不用的大程序，必要时按运行参考重开托管后端，从1024重试 |
| 提交内存不足 | 同一任务的`commit_headroom_GiB`低于6 | 按运行参考核对实际分页与提交上限，配置值不能代替已生效分配 |
| GPU显存不足 | 后端日志有CUDA显存分配失败 | 等队列清空并释放模型，检查其他GPU程序；从1024验证。CPU分页文件不能当作等速显存使用 |
| 多图或1536依然不稳定 | 上述配置已确认，仍对同一输入中断 | 保留失败任务ID与日志，作为该输入未通过；先使用已验证的1024或较少视图方案并明确限制，不能默认为完整1536/四图已通过 |



查看`runtime/memory_guard.json`中的`residency_trims`、`last_residency_trim`和`session_interrupts`；完整事件在`runtime/memory_guard.events.jsonl`。`last_interrupt`可能属于历史任务，必须比对任务ID，不能因旧记录还在就判断新任务失败。可用RAM是瞬时值；有一次测试通过不等于以后任何输入都不会触发保护。运行时不要手动删除`features-*.bin`映射文件。



[官方战斧与四视图机甲补充验证](../../../docs/evidence/historical-summary.json)记录原始输入、官方展示视频、本机1024/1536输出、启动配置、失败与重试、内存采样和质量限制。此处比较使用当前通用流程，不针对战斧或机甲修改生成参数。



自动回收接入正式内存管理进程后的官方机甲四图1536实测：207.2秒，实际1536几何及4K PBR完整导出；自动回收2次，本次保护中断0次，2秒采样的可用RAM最低约5.89GiB、提交余量最低约22.54GiB。测试脚本的独立回收辅助已关闭，使用的是随启动器运行的正式管理进程。它验证了该输入在当前后台负载下的完整执行，不承诺任意新输入都能容纳，也不把瞬时采样当作精确峰值。
